# GitDash v4.5.1 — release notes

Released 2026-09-27. This is the first published release of the 4.5 line (the previous release was
v4.2.9), so it contains everything from 4.5.0 as well as the 4.5.1 changes. The itemised list lives
in [`CHANGELOG.md`](../../CHANGELOG.md); this page explains what matters when you upgrade.

## Highlights

**A new interface.** Every screen follows the "Graphite console" design contract: a grouped sidebar
with an org switcher and API budget, a top bar with ⌘K search, and redesigned repository, workflow,
team, cost, alerts, settings and sign-in pages. A 90-second intro video plays from **Explore the demo**
on the sign-in page.

**Fewer GitHub API calls.** GitHub reads are cached per token, and replicas share results through a
Postgres table, so dashboards stay responsive well inside GitHub's rate limit. Refresh buttons still
fetch live data.

**Who sees what, in organization mode.** An admin puts people in fixed groups (`devops`, `security`,
`dev`, `pm`, `admin`) and decides which features each group can open. The server enforces it, every
change is audited, and people without a group wait on a page that moves on by itself once they are
added. People can sign in with GitHub or with a personal access token.

**New in 4.5.1:** the waiting page was redesigned. It shows where the person is in the process, gives
them their GitHub login and numeric id to send to an admin (one click to copy), and checks again every
15 seconds with a **Check now** button. Version badges now show the full version.

## Upgrading

### Standalone mode

Nothing to configure. Deploy the new version.

### Organization mode — read before deploying

Organization mode now **refuses to start** without these settings (`/api/health` answers 503):

| Setting | Why it is required |
|---|---|
| `DATABASE_URL` | Users, groups, grants and the audit log live in Postgres. |
| `GITDASH_ADMIN_GITHUB_IDS` | Someone must be able to reach `/admin` on day one. Use numeric ids (`gh api user --jq .id`), not logins. |

Recommended order:

1. Back up the database. First start runs two additive migrations (new tables only).
2. Set `GITDASH_ADMIN_GITHUB_IDS`, and `GITDASH_ALLOWED_ORGS` if sign-in should be limited to members
   of your organization(s).
3. Deploy with `GITDASH_RBAC_ENFORCE` unset or `false`. Everyone keeps their current access; only the
   admin pages are restricted.
4. Let people sign in, then give groups features under **Admin → Permissions** and put people in
   groups under **Admin → Users**.
5. Set `GITDASH_RBAC_ENFORCE=true` and redeploy. On Vercel, environment variable changes only apply to
   new deployments.

Helm users: chart `0.7.0` exposes these as `adminGithubIds` (a quoted string), `allowedOrgs`,
`rbacEnforce` and `secret.databaseUrl`; the values schema rejects organization mode without admin ids.

## Sign-in troubleshooting

When `GITDASH_ALLOWED_ORGS` is set, GitDash asks GitHub whether the signed-in account is an active
member of one of those orgs. If GitHub will not answer, sign-in is refused, because GitDash cannot tell
a member from a stranger. The server log records GitHub's reason. The usual causes:

- **The org restricts OAuth Apps.** An organization with *OAuth App access restrictions* hides membership
  from apps it has not approved, so every "Continue with GitHub" sign-in is refused. An org owner approves
  the GitDash OAuth App under the org's *Third-party access* settings. The same restriction also hides
  the org's private repositories from GitHub sign-ins.
- **A fine-grained PAT that belongs to the user, not the org.** Create it with the **organization as the
  resource owner** and grant *Members: read*. If the org requires approval for fine-grained tokens, an
  owner must approve it first.
- **A classic PAT the org does not accept.** Classic tokens need `read:org`, and some orgs reject classic
  tokens that live longer than 366 days.

## Known limitations

- A new grant can take up to a minute to show, because group lookups are cached for 60 seconds.
- The Cost page relies on the server to block access without the `costAnalytics` grant; the page itself
  does not re-check the flag.
- The admin screens do not page or debounce yet; they are sized for small teams.
