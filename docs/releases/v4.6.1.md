# GitDash v4.6.1 — release notes

Released 2026-09-29. Fixes the nightly pull-request sync, which working habits and the people alerts
depend on. Helm chart 0.7.4 declares appVersion 4.6.1. Adds database migration v11. See
[`CHANGELOG.md`](../../CHANGELOG.md) for the itemised list.

## Why

After 16 repositories were added to production's synced list, `/api/cron/sync-pr-facts` hit Vercel's
300 s limit (`FUNCTION_INVOCATION_TIMEOUT`) and most repositories got no pull-request data. Three problems
in that job, all older than 4.6.0:

1. **No deadline.** It ran until the platform killed it.
2. **No resume.** Backfill progress was only saved at the end of a repository's run, and a run capped at
   10 pages (1,000 pull requests) restarted at page 1 next time — a repository with more than 1,000 pull
   requests could never complete, despite the code comment saying it resumed.
3. **No real incremental mode.** The stored cursor was the oldest pull request processed, so the
   "stop at already-synced pull requests" check never fired: every night re-fetched every pull request
   with two detail calls each (tesda-backend: 728 GitHub calls per night).

## What changed

- The job stops starting new pages at 240 s. A repository cut short keeps what it stored.
- `sync_cursors.pr_backfill_page` (migration v11) records the next page to read during a backfill; the
  next run continues there. Page shifts in between cause re-reads, never skips.
- `pr_sync_cursor` is now a high-water mark: the newest pull-request update at the start of the last full
  pass. After the backfill, a run reads pages until it reaches the mark and fetches details only for pull
  requests updated after it — usually one list call per repository.
- Repositories whose backfill is complete are synced first; those still backfilling take the rest of the
  budget.
- Working habits' owner view says "No repositories of this owner are synced yet" instead of
  "No merged pull requests in this window" when that is the cause.

## Notes for operators

- Migration v11 runs on the first request after deploy. It adds one nullable column and moves the cursor
  of every repository whose backfill is complete to two days ago, so their first run re-reads only recent
  changes. Take a Neon branch or `pg_dump` first as usual.
- Repositories still backfilling may need several nights (or manual runs of the cron with the
  `CRON_SECRET` bearer) to complete. Each response shows `backfillComplete` and `stoppedAtDeadline` per
  repository.
- People alerts (including Oversized commits) stay quiet for a repository until its backfill is complete.
