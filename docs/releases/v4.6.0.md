# GitDash v4.6.0 — release notes

Released 2026-09-29. Adds **working habits**: how well each engineer keeps commits and pull requests
small. Helm chart 0.7.3 declares appVersion 4.6.0. This release adds database migration v10 and a third
nightly cron. See [`CHANGELOG.md`](../../CHANGELOG.md) for the itemised list.

## Why

The team standard is small commits and small pull requests. A commit that changes more than 10 files or
more than 200 lines is hard to review; so is a pull request with more than 20 commits. Leads had no way
to see who follows the standard and who needs coaching.

## What it shows

On **Team insights**, for one repository or all of its owner, over 30 or 90 days:

- per person: commits, commits over the limit (count and share), merged pull requests, and pull requests
  over the commit limit;
- the oversized commits and pull requests themselves, linked to GitHub, filterable by person;
- a freshness and coverage line ("Updated 6h ago · 38 of 40 merged pull requests analysed").

On a **contributor profile**, a card with that person's share and their five largest oversized commits.
Engineers always see their own card, even without the feature.

There are no rank numbers. It is meant for coaching, not for ranking people.

## How it counts

- Only **merged** pull requests, by merge date.
- Commits are measured **inside the pull request that carried them**. Measuring on the default branch
  would misread squash merges: one squash commit stands for many small commits. Measured on a real
  repository, 4 of the last 40 merges in one service and 14 of 40 in another were squash or rebase merges.
- A commit shared by stacked pull requests counts once, for the pull request merged first.
- Merge commits and bots (`[bot]` accounts, dependabot, renovate, github-actions) are left out.
- When GitHub cannot count a very large commit's files, its lines alone decide.
- A commit whose email is not linked to a GitHub account is credited to the pull-request author and
  marked "via PR author".

**Not counted:** commits pushed straight to the default branch, and repositories without GitHub Actions
history (GitDash does not sync their pull requests; the section says "Not tracked").

## Checked against GitHub

On `tesda-backend`, 90 days: 100 merged pull requests, 396 commits. An independent script recomputed every
figure from the GitHub REST API. It compared 5 figures for each of 4 engineers and found **0 mismatches**. The sync
took 20 s and 10 GraphQL queries (1 rate-limit point each).

## Access

- New feature `workingHabits`, **on by default**, granted per group in organization mode. Admins always
  have it.
- `GET /api/db/working-habits` checks the grant itself, whatever `GITDASH_RBAC_ENFORCE` says. Without the
  grant, a user can read only their own login. The owner-wide view includes only repositories the viewer's
  own token can open.
- The new alert metric and its events are hidden from users without the grant.
- The Monday digest line carries **totals only, no names**, because the digest leaves GitDash by email
  or Slack.

## Alerts and digest

- New alert metric **Oversized commits** (`oversized_commit_pct`): the share of oversized commits in pull
  requests merged within the window. It stays quiet with fewer than 5 commits or while the window is not
  fully analysed. It is evaluated once a day after the commit sync, so use a window of 24 hours or more.
  An organization-wide rule reports the first repository that breaches in a window.
- The Monday leadership digest gains one line, for example: "Working habits (7 days to Mon 2026-09-28
  04:47 UTC): 34% of 212 commits were over the size limit; 2 pull requests had more than 20 commits; 38 of
  40 merged pull requests analysed." If computing it fails, the digest is sent without it.

## Notes for operators

- **Back up the database before upgrading.** Migration v10 runs on the first request after deploy. It is
  additive (three nullable columns on `pr_facts`, tables `pr_commit_facts` and `working_habits_settings`),
  but take a Neon branch or `pg_dump` first.
- **New cron `/api/cron/sync-commit-facts`**, daily at 04:47 UTC, with the same `CRON_SECRET` bearer and
  `GITHUB_TOKEN` as the others. On Vercel it is registered from `vercel.json`. **Helm and Docker
  deployments must schedule it themselves**, at least 30 minutes after `/api/cron/sync-pr-facts`.
- The first nights backfill 90 days: up to 200 pull requests per repository per run, stopping new work
  after 240 s. Until it finishes, figures show "backfill in progress". You can run the cron by hand with the
  bearer to speed it up.
- Grant `workingHabits` to the lead groups in Admin → Permissions.
- Thresholds: Settings → Working habits (organization mode). Standalone uses 10 files / 200 lines /
  20 commits.

## Known limitations

- A pull request that GitHub never returns (for example, deleted) is retried every night and keeps its
  90-day window "incomplete", which silences the alert for that repository until the PR ages out.
- Commits stored with the pull-request author as fallback are not re-linked if the engineer later links
  their email to GitHub.

## Also in this release

- Contributor profile: the person lookup runs alongside the searches, the owner's account type is cached
  for a day, and responses carry a `Server-Timing` header (durations only).
